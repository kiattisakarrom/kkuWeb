# Report > Workload

พัฒนา 21 ตุลาคม 2026 เปิดที่ `/ipd/reports/workload` ผ่าน session เดิม เป็นรายงานดูข้อมูลอย่างเดียว ใช้โหมด `workloadIPD` ตามเมนู Report > Workload ไม่ใช่ Workload ของเมนูรายงานหน่วยผลิต > IV

## ต้นฉบับและฟอร์ม

- อ้างอิง `ctx/Workload/ucWorkload.vb:Showdata`, Designer, `ctx/class/cls_Worklaod.vb`, `Pharmcare/frmPharmacist.vb`, `Login/class/ClsUsers.vb:dgvUser` และ `Report/Workload/clsWorkloadNew.rpt`
- แผงซ้ายมีช่วงวันที่เริ่ม/สิ้นสุด ค่าเริ่มต้นวันนี้ทั้งคู่ กลุ่ม “ชื่อผู้ใช้งาน :” ปุ่ม “เลือกผู้ใช้งาน” และปุ่ม “ค้นหา” แบบเดิม
- เปิดหน้าแล้วไม่โหลดรายงานเอง ปุ่มค้นหาจะค้นหาทุกคนเสมอ ส่วนปุ่มเลือกผู้ใช้งานเปิดหน้าต่าง Pharmacist เลือกแล้วค้นหารายคนทันทีตาม Windows ไม่คงตัวกรองรายคนไว้กับปุ่มค้นหาทั้งหมด
- หน้าต่างเลือกผู้ใช้งานมีคอลัมน์ รหัส / ชื่อ - นามสกุล กรองชื่อหรือรหัสที่ขึ้นต้นตามข้อความ ตัดผู้ใช้ `0201` และชื่อที่เป็น null ออก ไม่มีรหัสผ่านหรือข้อมูลบัญชีอื่นส่งมาใน API
- ด้านขวาเป็นตัวแสดง PDF แบบ canvas มีดาวน์โหลด PDF, เปลี่ยนหน้า และซูม ไม่เรียกเครื่องพิมพ์จริง วันที่เปลี่ยนจะยกเลิกคำขอและซ่อนผลเก่า ไม่ให้รายงานผิดเงื่อนไข
- ไม่พบข้อมูลหรือเกิดข้อผิดพลาดแสดงหน้าต่าง “ระบบแจ้งเตือน”

## วิธีนับที่คงตาม Windows

รวมผล 3 ชุดใน SQL batch เดียวเพื่อลดการเดินทางระหว่างเว็บกับฐาน โดยใช้ MSSQL ทั้งหมด ไม่มี MySQL

1. Pharmcare: `ms_drpheader` ของ IPD ที่ GroupOfCareCd และ Usercreatecode ไม่เป็น null ช่วง `[DateD/C] BETWEEN from AND to` รวม `COUNT(DISTINCT OrderNo)` ตามผู้ใช้และ GroupOfCare ใช้ชื่อ firstname + lastname และ TblOfGrOfCare จาก LEFT JOIN
2. กิจกรรมปัจจุบันจาก `prescription` / `packagemaster`
3. กิจกรรมย้อนหลังจาก `[BACKUP].dbo.prescription` / `[BACKUP].dbo.packagemaster` แล้วนำมาบวกเพิ่ม ไม่ตัดรายการที่ซ้ำข้ามสองฐานออก เพราะต้นฉบับบวกแยกกัน

กิจกรรมต้องมี genorderdatetime, confirmuserid และ fromlocationname = `ห้องยา IPD[001]` ตามต้นฉบับ ไม่เพิ่มเงื่อนไขห้องยาตาม session หรือวอร์ด

- Screening_WL: distinct prescriptionno / confirmuserid
- Checkout: distinct prescriptionno / checkoutuserid ที่ไม่ null ไม่บังคับ checkoutdatetime เพราะต้นฉบับไม่ได้กรอง
- LED: distinct prescriptionno / leduserid ที่ไม่ null และไม่เป็น 0 พร้อม leddispensedatetime
- HAD: distinct prescriptionno / haduserid ที่ไม่ null และไม่เป็น 0 พร้อม haddispensedatetime
- รวมตามรหัสผู้ใช้และชื่อ GroupOfCare หลัง trim โดยรักษาชื่อ/รหัสกลุ่มที่พบครั้งแรก ค่า SAn เป็น 0 ตามฟอร์มต้นฉบับ
- โหมดทุกคนแสดงเฉพาะคนที่มีกิจกรรมอย่างน้อยหนึ่งชนิด แต่สร้างทั้ง 4 หมวดของคนนั้นรวมหมวดที่เป็นศูนย์ โหมดรายคนสร้างทั้ง 4 หมวดแม้ไม่มีการทำงาน ถ้ามีผู้ใช้นั้นใน ms_users

### เวลาและพฤติกรรมเดิมที่ต้องทราบ

- ใช้เวลา Asia/Bangkok ตอนกดค้นหา: ตั้งแต่ 08:00 เลือกจากวันเริ่ม 08:00 ถึงวันถัดจากวันสิ้นสุด 07:59:59; เวลา 00:01–07:59 เลื่อนวันเริ่มย้อนหลังหนึ่งวันและจบวันสิ้นสุด 07:59:59
- ช่วง 00:00:00–00:00:59 ต้นฉบับไม่เติมเงื่อนไข ordercreatedate เว็บยังคงพฤติกรรมนี้เพื่อให้ผลตรงกัน มี unit test แยกไว้
- Pharmcare ใช้ DateD/C แบบ datetime เทียบวันที่สิ้นสุดที่เวลา 00:00 ตาม SQL เดิม ไม่เปลี่ยนเป็นครอบคลุมทั้งวัน หากต้องการเปลี่ยนกติกานี้ต้องตกลงเกณฑ์ใหม่ก่อน
- ถ้าอ่าน BACKUP ไม่ได้จะรายงานข้อผิดพลาด ไม่แสดงยอดปัจจุบันอย่างเดียวเป็นยอดสมบูรณ์

## ตารางและ PDF

- ใช้ CrossTab ตาม `clsWorkloadNew.rpt`: แถวเป็น **Fname** ไม่ใช่รหัส ดังนั้นผู้ใช้คนละรหัสที่ชื่อแสดงเหมือนกันจะรวมในแถวเดียวกันตาม Crystal
- คอลัมน์ประเภทงานเกิดจากข้อมูลจริง เรียงแบบ English locale ตามแบบเดิม ไม่กำหนดเพียง 4 กิจกรรม และมี GroupOfCare ของ Pharmcare รวมด้วย
- คอลัมน์ยอดรวมอยู่ซ้ายก่อนประเภทงาน แถว Pharmacist ด้านบนเป็นยอดรวมทุกคน ช่องไม่มีรายการเป็น 0
- PDF A4 แนวนอน 842 × 595 pt ใช้ส่วนหัว/โลโก้/ชื่อโรงพยาบาลและที่อยู่จากแบบ Crystal เดิมโดยตรง ฝัง Sarabun สำหรับวันที่ ตาราง และท้ายกระดาษเพื่อแสดงไทยได้ครบ
- คงความกว้างแถวชื่อ 149.5 pt, ยอดรวม 60 pt, ประเภทงาน 96 pt ตามแบบเดิม คอลัมน์ 6 ประเภทแรกอยู่หน้าแรก ส่วนเกินต่อแนวนอนครั้งละ 8 คอลัมน์ หน้าแนวนอนต่อไม่ซ้ำชื่อแถวตาม `EnableRepeatRowLabels=False` ของ RPT
- ปรับข้อความหัวคอลัมน์และชื่อยาวให้ขึ้นบรรทัดครบแทนการตัดทิ้ง วัดความสูงด้วยฟอนต์เดียวกับที่วาด และใช้ความสูงแถวเดียวกันทุกหน้าแนวนอนเพื่อไม่ให้ตัวเลขเหลื่อมคน
- แบ่งแถวแนวตั้งเมื่อเต็มหน้า พร้อมหัวคอลัมน์ซ้ำ ใส่วันที่พิมพ์และเลขหน้าทุกหน้า รวมหน้าต่อแนวนอนซึ่งแบบเดิมไม่แสดง footer
- อ่านข้อมูลครั้งเดียวแล้วใช้ Blob เดียวกันในการดูและดาวน์โหลด ไม่ค้นหาข้อมูลใหม่ตอนกดดาวน์โหลด

## API / ทรัพยากร

- GET `/api/reports/workload/users` ไม่รับตัวกรองอื่น
- POST `/api/reports/workload/pdf` รับเฉพาะ `{from,to,userId}` โดย userId ว่าง = ทุกคน, ใช้ bound SQL parameters และไม่รับข้อมูลเซลล์จาก browser
- ต้องมี IPD session, no-store, มี X-Report-Pages / X-Report-Rows สำหรับ viewer
- ไม่มี INSERT/UPDATE/DELETE, Robot, OCS หรือสั่งพิมพ์
- `back/assets/reports/workload/template.pdf`, `layout.json`, `header.png` สร้างจากแบบเดิมและข้อมูลจำลองเท่านั้น ไม่มีข้อมูลผู้ป่วยหรือผู้ใช้งานจริง
- `tools/export-workload-template.ps1` ใช้เฉพาะเตรียมทรัพยากรในเครื่อง ไม่ถูกเรียกโดยเว็บ ผู้ใช้อนุญาตการยกเว้น execution policy เฉพาะ process สำหรับสคริปต์นี้แล้ว ไม่เปลี่ยน policy ถาวร
- Server ที่ deploy ใช้ Node เท่านั้น ไม่ต้องติดตั้ง Crystal หรือเปิดสิทธิ์รัน PowerShell

## ผลตรวจ

- Backend ผ่าน **240/240 tests**, รวม Workload 8 tests; frontend targeted ESLint และ production build ผ่าน
- SQL เปรียบเทียบกับคำสั่ง StringBuilder ที่อ่านตรงจากซอร์ส Windows โดย `tools/check-workload-native.cjs`: ผลทุกแถวตรงกันทั้งทุกคนและรายคน ช่วง 2026-10-21 พบ 142 แถวก่อน pivot, 34 ชื่อ, 10 ประเภทงาน ยอดรวม 3,339, หน้าต่างเลือกผู้ใช้ 344 รายการ การอ่านรายงานครั้งแรกประมาณ 5.7 วินาทีรวมโหลดผู้ใช้ (เป็นค่าตรวจครั้งเดียว ไม่ใช่ SLA)
- ตัวเลข PDF ข้อมูลจำลองเว็บตรงกับทุกเซลล์ของ PDF Crystal เดิมทั้ง 2 หน้า รวมทดสอบชื่อซ้ำต่างรหัสและค่าศูนย์
- ข้อมูลจำลอง 80 คน × 10 ประเภทงาน สร้าง 12 หน้า ตรวจครบ 800 เซลล์ ชื่อครบ 80 คน ปลายชื่อยาวครบ 5 แห่ง และไม่มีตัวอักษรเลยขอบกระดาษ ตรวจภาพหน้าแรก/หน้าต่อ/หน้ากลางแล้ว
- Browser เปิดผ่าน Report > Workload ได้ ฟอร์มเริ่มต้นถูกต้อง เลือก/กรองผู้ใช้ 344 รายการได้ รายงานจริงแสดง PDF 6 หน้าและเปลี่ยนหน้าได้ รายงานรายคนแสดงได้ พร้อมตรวจกรณีไม่พบข้อมูล
