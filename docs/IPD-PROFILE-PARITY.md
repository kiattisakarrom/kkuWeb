# ข้อมูลด้านบนและ Medication Profile — 19 ตุลาคม 2026

อัปเดต 20 ต.ค.: ตาราง Medication Profile เหลือ 60 คอลัมน์ตรง Designer, LAB/Note DRP ด้านขวาตรงชุด 8/29 คอลัมน์แล้ว ดู [สถานะล่าสุด](IPD-READONLY-STATUS-2026-10-20.md) แทนการเพิ่ม High Alert/Protocol ที่ native ซ่อนในบันทึกเดิมด้านล่าง

ปรับกรอบเดิมใน `FrmProfile` เทียบ `Dispense/ucAddOrderdispense.showpatientlab` และ `ucMedicationprofile.showorderdetail` / Designer ของ Windows ที่ผู้ใช้ให้มา ทุกเส้นทางเป็นการอ่าน ไม่เพิ่ม mutation หรือเรียกฮาร์ดแวร์

## ข้อมูลผู้ป่วย

- คงชื่อ HN/AN อายุ สิทธิ์ วอร์ด ห้อง เตียง ที่อยู่ แพทย์ การวินิจฉัย จำนวนใบยา และประวัติแพ้ยา เพิ่มรหัสแพทย์/สิทธิ์ วันจำหน่าย และ ANC
- เลือกค่าที่บันทึกล่าสุดใน `ms_patientlabresult` ของ AN/HN และผลล่าสุดรายชนิดของ HN ใน `ms_labresult` ย้อนหลัง 7 วันตามเกณฑ์ native: Creatinine*, eGFR (CKD-EPI), WBC, Neutrophil %, Band form Neutrophil %; ใช้ผล LAB เมื่อใหม่กว่าค่าที่บันทึก หรือค่านั้นว่าง WBC ไม่ใช้ผลที่มีขีดตามต้นฉบับ
- BSA = sqrt(abs(weight) * height / 3600); CrCl ผู้ใหญ่อายุ >=15 ใช้ ((140-age)*abs(weight)/(72*Scr))*ตัวคูณเพศ (ชาย 1, หญิง .85), เด็กใช้ .413*height/Scr; ANC = WBC*Neutrophil*10 ตาม source ซึ่งไม่ได้รวม Band form คำนวณเพื่อแสดงเท่านั้น ไม่ INSERT/UPDATE ค่าเหล่านี้
- ไม่เปลี่ยนข้อมูลว่าง/ผลข้อความเป็นศูนย์เพื่อคำนวณ ไม่หารด้วย Scr=0; หากข้อมูลไม่พอแสดงขีด เก็บ BSA/CrCl ที่บันทึกเดิมใน response แยกจากค่าคำนวณ และมี tooltip แหล่งข้อมูล/เวลา
- แก้ความผิดพลาดต้นฉบับที่บางกิ่งนำวันที่ Band form มาแสดงเป็นค่าผล โดยอ่านค่าผลตรวจจริง
- Protocol ด้านบนของ Windows เป็นตัวเลือกสำหรับเพิ่มคำสั่งยา ไม่ใช่ช่องสรุป Protocol ของ admission เว็บจึงแสดง **Protocol ของรายการยาที่เลือก** แบบ read-only กดชื่อยาในตารางแล้วแสดงรหัส/ชื่อจริงจาก `ms_protocol`; ไม่เดาว่าทั้ง admission ใช้ Protocol ล่าสุดตัวเดียว และล้างเมื่อเปลี่ยนชุดข้อมูล

## Medication Profile

- เพิ่มสถานะตาม `checkscreen` ของ Medication Profile โดยอ่านใบ `prescription` ของ meditemindex / AN / HN ในรอบและ active ward ไม่บังคับ genorderdatetime เหมือน native เลือกเลขใบแรกเรียงตามเลขใบและนับใบแบบ batch ไม่ query ต่อแถว (ต่างจาก `checkscreen` ในหน้ารายการสั่งยาที่ใช้ key ผิด จึงไม่ได้เปลี่ยนหน้านั้น)
- เพิ่มใบอนุมัติจาก `ms_Allow` พร้อมช่วงวัน/เหตุผล, DUE Online ล่าสุดต่อรหัสยา, statuscal/dosecal, varymeal, ผู้บันทึก, เวลาแปรผัน, วันที่กิน/วันเว้นวัน, First dose status/count, Continue, เวลาเริ่ม/หยุด/วัน, High Alert และรหัส/ชื่อ Protocol รวมถึงข้อมูลเดิมทั้งหมด
- เลือกชื่ออังกฤษจาก master ก่อนชื่อที่บันทึก และสีชื่อจาก ARGB ของ `ms_drug` ตาม native; ข้อมูลสำคัญที่ซ่อนไว้ใน Designer เช่น High Alert/Protocol เพิ่มเป็นคอลัมน์อ่านได้
- ชื่อ [OFF]/[Hold], จำนวนจ่ายที่แสดงเป็น 0 เมื่อ Off/Hold ตาม native พร้อมคงจำนวนที่บันทึกเดิมในคอลัมน์แยก; จำนวนที่ใช้เลือก varymeal ถ้ามี ไม่แทนค่าศูนย์ด้วยค่าว่าง
- สีน้ำทะเลเมื่อเปิดค่าพิมพ์/เครื่อง, เหลืองเมื่อวันเริ่มตรงรอบ, เขียวเมื่อมีใบในรอบ, เทาเมื่อ Off/Hold; ใบอนุมัติ Pass เขียว / Hold แดง / Con เหลือง; Type C/CS/O และสีช่องขนาด/หน่วย/วิธีใช้ตามต้นฉบับ
- DUE Online ใช้ status ที่บันทึก 1=อนุมัติ, 2=ไม่อนุมัติ, ว่าง=รออนุมัติ แก้กิ่งสี native ที่ตรวจคำว่า “อนุมัติ” ก่อน “ไม่อนุมัติ” แล้วทำให้สีผิด ไม่ใช้ข้อความย่อยตัดสินสถานะ
- DUE โหลดแยกจากยา API ล่มแสดงโหลดไม่ได้และลองใหม่ ไม่บังคับตารางยารอ ไม่แสดงว่าไม่มี DUE แทนข้อผิดพลาด
- เมื่อต้นทางมีใบอนุมัติซ้ำ เลือก AllowCd ล่าสุดอย่างแน่นอน แทน native ที่เลือกแถวแรกโดยไม่ ORDER BY; lookup master ใช้ TOP 1 และ MRC ใช้ EXISTS เพื่อไม่ทำให้แถวยาซ้ำ
- คงกลุ่ม IPD/IV/Chemo/TPN รอบยา/Off mode และการกลับหน้าเดิม ปุ่มสร้าง/บันทึก/Off/Hold/เครื่อง และ checkbox แสดง flag ไม่เปิดให้เปลี่ยนข้อมูล

## ข้อจำกัดและความต่างที่ตั้งใจ

ไม่ทำ side effects ระหว่างเปิดหน้าตาม native: ไม่ auto-Off, เลื่อน odddatetime, reset firstdosestatus หรือเปลี่ยน AllowStatus หมดอายุ สถานะเหล่านี้อ่านค่าที่บันทึกจริงเท่านั้น คำว่า “จัดแล้ว” เป็นการแสดงตามใบยาในรอบของ native ไม่ใช่หลักฐานให้ยาแก่ผู้ป่วย

ขอบเขตนี้ใช้ MSSQL; DUE Online ยังต้องตรวจข้อมูลจริงเมื่อ API โรงพยาบาลเข้าถึงได้ตามงาน IHOS DUE เดิม ส่วน MySQL หน้าอื่นยังเตรียมไว้ตามข้อกำหนดเดิม ไม่มีการเปลี่ยนแหล่งข้อมูลหน้านั้น
