# Screening — ยากลับบ้านรอจัด (ดูข้อมูล)

ตรวจ 18 ตุลาคม 2026 จาก Windows `Screenning/ucScreenningMain.btnTakeHome_Click`, `ucScreenTakeHome.vb` และ Designer, `clsPrescription.getgroupWard/getPresHeader` และ `clspackagemaster.getForgenorder`

## ขอบเขตหน้าเว็บ

เปิดปุ่ม **ยากลับบ้านรอจัด** (`mode=take-home-wait`) ในเมนู Screening เดิม ใช้สามตารางตาม native: วอร์ดซ้าย → หัวใบขวาบน → รายการยาขวาล่าง เริ่ม **ทุกห้องยา** เพื่อแสดงทุกหอที่มีรายการเหมือน Windows และยังเลือกกรองห้องจริงจาก `ms_room` ได้ ไม่เปลี่ยนห้อง login ของ IPD — ดู [ผลแก้หอแสดงไม่ครบล่าสุด](IPD-TAKE-HOME-ALL-WARDS.md)

ค้น AN/HN/เลขใบแบบตรงกันข้ามวอร์ดในห้องและรอบที่เลือก แสดงวอร์ดเฉพาะที่มีรายการตามเงื่อนไขยอดวอร์ด เลือกวอร์ดแล้วโหลดใบของวอร์ดนั้น เลือกใบแล้วอ่านยาเฉพาะใบ ห้อง วอร์ด HN/AN ที่ backend ตรวจจากหัวใบ ดับเบิลคลิกหรือปุ่มรายละเอียดเปิดหน้าผู้ป่วยเดิม และกลับคง mode/ห้อง/วัน/รอบ/คำค้น/วอร์ด/เลขใบ

เปลี่ยนห้อง วัน คำค้น หรือโหมด ล้าง selection/detail เก่าและยกเลิกคำขอค้าง มี loading/error/empty แยกกัน ฐานข้อมูลล้มเหลวไม่แสดงว่าไม่มีคิว ใบที่มีแต่ Stat/ยา Off อาจมีหัวใบแต่รายการยาว่างได้ตาม native ไม่ใช่ใบหายหรือ error

ดูข้อมูลอย่างเดียว ปุ่มจัด ส่งเครื่อง ยกเลิก พิมพ์ และ Reprint ปิด ไม่มีสร้างยา สร้าง OCS file หรือเปลี่ยน gen/print status ผ่านการเปิดหน้า เลือกแถว หรือดับเบิลคลิก ปุ่ม **ยากลับบ้านจัดแล้ว** เปิดแล้วตาม S09 — ดู [ผลตรวจจัดแล้ว](IPD-SCREENING-TAKE-HOME-FINISHED.md)

## เงื่อนไข native ที่รักษาแยกตามระดับ

ทุกระดับใช้ `prescription.genorderdatetime IS NULL` และ **`ordertype='1'`** ไม่ hardcode วอร์ด 31 และไม่ตกไปใช้ Stat/Continue query

| ระดับ | เงื่อนไขเฉพาะ | ปลายช่วงตั้งแต่ 08:00 กรุงเทพฯ |
|---|---|---|
| ยอดวอร์ด (`Showward`) | non-Stat: ISNULL(frequencycode,'') NOT IN S/E/STAT; ไม่ตัด Off/Hold หรือ inactive ward; นับ distinct ใบต่อวอร์ด | วันถัดไป 07:59:00 |
| หัวใบ (`ShowPrescriptionHeader`) | วอร์ดที่เลือกต้อง active; **ไม่ตัด Stat/Off/Hold**; group ตามวันสร้าง/เลขใบ/HN/AN/ชื่อ/วอร์ด/เตียง/type/ห้อง/วัน gen | วันเดียวกัน 23:59:00 |
| ยาในใบ (`ShowPrescriptiondetail`) | non-Stat และ voiddatetime IS NULL; ไม่ตัด Hold; จำกัดใบ/วอร์ด/ห้อง/ตัวตนจาก server | วันถัดไป 07:59:59 |

ทุกช่วงเริ่มวันที่เลือก 08:00 ก่อน 08:00 จะถอยวันเริ่มหนึ่งวัน และจบวันที่เลือก 07:59:00 สำหรับยอด/หัวใบ หรือ 07:59:59 สำหรับยา รวมกรณีวันที่ย้อนหลัง ใช้ `BETWEEN` แบบรวมปลายช่วงตามต้นฉบับ ไม่ขยายช่วงเวลาเงียบ ๆ backend ส่ง workdate ที่ใช้จริงให้คำขอลูกเพื่อ pin รอบเดียวกัน และคืน `wardEnd/headerEnd/end` แยกไว้ หน้าจอแสดงปลายช่วงหัวใบด้วย

ยอดวอร์ดจึงไม่จำเป็นต้องเท่าจำนวนแถวหัวใบ เช่น มีใบหลังเที่ยงคืน หรือหัวใบมี Stat ด้วย หอที่มีเฉพาะ Stat จะไม่เข้ารายการวอร์ดตาม source แม้ query หัวใบของหอนั้นจะพบได้หากเรียกโดยตรง การค้นหาในเว็บยังใช้เงื่อนไขของแต่ละระดับนี้

## ส่วนที่เพิ่ม/แก้จากต้นฉบับตามขอบเขต viewer

- Windows Take-home ไม่กรองห้องยา เว็บเริ่มทุกห้องโดยไม่ใส่ fromlocationname filter เช่นกัน เมื่อเลือกห้องเฉพาะจึงกรอง **fromlocationname = roomname+'['+roomcode+']'** จาก master ที่ backend ตรวจ ครบยอด/หัวใบ/ยา
- หัวใบ recheck ก่อนอ่านยา ปฏิเสธเมื่อมีหลาย HN/AN ในเลขใบเดียวกัน และไม่รับ client HN/AN override รายการยาถูกผูกวอร์ด/ห้อง/ผู้ป่วยเพิ่มเติมจาก native ที่ใช้เลขใบเป็นหลัก
- แสดง **แถวยาที่บันทึกใน prescription** พร้อม dose/qty, หน่วย, วิธีใช้, ความถี่, เวลา/ข้อความ, varymeal/varymealtime, Off/Hold และ flag เดิม ไม่รันส่วนคำนวณ/แตกจำนวนซอง JVM หรือสร้างแถวสำหรับพิมพ์ของ Windows จำนวนแถวยาจึงไม่รับรองว่าเท่าตารางจำลองซองเครื่อง แต่ชุดข้อมูลยาที่ผ่านเงื่อนไขก่อนแตกซองตรงกับ source ที่ตรวจ ขอบเขตนี้สอดคล้องกับรุ่นอ่าน Stat/Continue ที่ทำก่อนหน้า
- ที่เก็บ/เส้นทางจาก master แสดงเป็นข้อมูลตั้งค่า ส่วน print/send flag แสดงค่าที่บันทึก ไม่คำนวณสถานะสำหรับงานส่งหรือพิมพ์ใหม่ ไม่มีการแก้ค่าต่างมื้อหรือแปลงเวลาเป็นคำสั่งเครื่อง
- หน้านี้อ่าน MSSQL ไม่ต้องเพิ่ม MySQL endpoint ตาม flow แสดงคิวที่ตรวจ ไม่สร้างข้อมูลสมมติทดแทนข้อมูลจริงที่ไม่มี

API GET `/api/ipd/screening/wards`, `/prescriptions`, `/prescriptions/:prescriptionno` ใช้ JWT และตัวกรอง mode/room/date/search/ward/round แบบเดิม ต้องระบุ ward ในการอ่านหัวใบและยา รองรับห้อง all เป็นค่าเริ่มต้น แต่ไม่รับ status/type filters ของ Screen All โหมดอื่นยังใช้ query เดิม ใช้ pool ร่วมและ parameters ทั้งหมด

## ผลตรวจ

- **113 backend tests ผ่าน** รวมชุดเดิม และช่วงเวลาสามระดับ/ก่อน-ตรง 08:00/leap day/ข้ามปี/pin รอบ, query routing, server HN/AN, empty drugs ที่ถูกต้อง, missing/ambiguous header, auth/บริบท/validation/ห้ามเขียน และแยก empty จาก 503
- Frontend production build และ ESLint ของไฟล์ที่แก้ผ่าน
- ฐานจริงวันที่ 18 ต.ค. 2026 ห้อง 001/002 ไม่มีคิวที่เข้าข่าย ยอดว่างตรงกับ SQL native บวกห้องเดียวกัน รวมตรวจห้อง 001 ในรอบก่อน 08:00 ว่างเช่นกัน ไม่มีการใส่ข้อมูลแทน
- ตัวอย่างย้อนหลังที่มีรายการ วันที่ **17 ต.ค. 2026 ห้อง 005: 1 วอร์ด / 1 หัวใบ / 1 แถวยา** เทียบยอดรายวอร์ด fields หัวใบ และ saved item fields กับ SQL native ผ่าน ตรวจ API จริงหลัง restart ได้ 200 ทั้งสามระดับ และเอาเลขใบเดิมไปอ่านห้อง 001 ได้ 404
- API ที่วัดครั้งนี้ใช้ประมาณ **103–529 ms ต่อคำขอ** จากคิวว่างและตัวอย่างย้อนหลัง ไม่ใช่ p95 หรือผลทดสอบโหลดพร้อมกันหลายผู้ใช้
- Browser ข้อมูลสมมติ: โครงสามตาราง, ห้องต่างกัน/ห้องว่าง, ค้นข้ามวอร์ด, ใบ Stat-only/Off-only มีรายการยาว่างโดยไม่ error, ยา Hold/ค่าศูนย์, เปิดผู้ป่วยและกลับคงห้อง/ใบ, ฐานข้อมูลจำลองขัดข้องแสดง alert และล้างใบเก่า ผ่าน เว็บจริงเข้าเมนูได้และแสดงคิวว่างห้อง001ตามฐาน
- ภาพ `ipd-screening-take-home-wait-demo.png` ใช้ข้อมูลสมมติทั้งหมด ไม่เก็บ PHI/token ลงเอกสาร ภาพ หรือ Git

ยังต้องตรวจรับข้อมูลหลายวัน/หลายห้องและโหลดผู้ใช้จริงเพิ่มเติม ไม่รวมการรับรองจำนวนแถวซองเครื่องหรือขั้นตอนจัด/ส่ง/พิมพ์
