# รายการสั่งยาในรายละเอียดผู้ป่วย — 18 ตุลาคม 2026

อัปเดต 20 ต.ค.: แก้หัวใบ/รายละเอียด 61 คอลัมน์/checkbox/สถานะ และเพิ่มประวัติคู่ยาแล้ว ผลและกติกาล่าสุดใน [สถานะ 20 ต.ค.](IPD-READONLY-STATUS-2026-10-20.md) แทนข้อจำกัดการแสดงผลและสถานะหัวใบของบันทึกเดิมด้านล่าง

ปุ่ม “รายการสั่งยา” ใน `FrmProfile` เปิดส่วนล่างแบบ `ucMedicationHistory`: วันที่และใบสั่งยาทางซ้าย หัวใบ/รายการยาทางขวา กรอบข้อมูลผู้ป่วย LAB/DRP เมนูหลักและปุ่มกลับยังอยู่ ไม่เปิดฟอร์มสร้าง/แก้/ลบ/Off/Hold/พิมพ์

## การเลือกข้อมูล

- เลือกวันที่เริ่มรอบด้วย date picker หรือรายการวันที่ที่มีใบสั่งยาจริงของ AN นั้น
- รอบ 08:00:00–07:59:00 วันถัดไปตาม `ucMedicationHistory.showgroupdateorder`; ก่อน 08:00 วันปัจจุบันใช้รอบวันก่อนตาม helper เดิม ส่วนวันที่ย้อนหลังระบุวันเริ่มรอบชัดเจน
- วันที่ที่มีใบยานับด้วยรอบเดียวกัน ไม่นับแถวที่อยู่ในช่องว่างหลัง 07:59:00 ถึงก่อน 08:00:00 ของ source เดิม
- รายการใบจาก `prescriptionheader` ไม่ join detail ให้จำนวนใบซ้ำ; รวมจำนวน detail/เวลาส่งต่อ/เวลาตรวจใน SQL ไม่มี request ต่อใบเพื่อเช็กสถานะ
- กดแถวหรือปุ่มเลขใบเพื่อดู `prescriptiondetail` ของใบนั้น รวมรายการที่ Off/Hold แล้วตาม `get_msdetailHis` ไม่มีเงื่อนไขตัดยาจาก Medication Profile ปัจจุบัน
- แสดงผู้บันทึก แพทย์ หอผู้ป่วยบนใบ วันที่อ่าน/ยกเลิก ราคารวมบนใบ และข้อมูลยาจาก detail กับ master หน่วย/วิธีใช้/ความถี่/เวลา
- หอผู้ป่วยบนใบเป็นข้อมูลประวัติ อาจต่างจากวอร์ดปัจจุบันที่ใช้ตรวจขอบเขตการเปิดผู้ป่วย
- เปลี่ยนวันล้างใบเดิมและรายการยาเดิมทันที ยกเลิก request เก่า ไม่แสดงข้อมูลจาก response ที่ไม่ตรงวันที่/เลขใบ
- วันที่และเลขใบที่เลือกอยู่ใน query (`view`, `rxDate`, `rx`) ทำให้ refresh หรือสลับ Medication Profile กลับมาได้ ส่วนกลับหน้ารายการผู้ป่วยล้างเฉพาะ key ของหน้ารายการสั่งยา และคงวอร์ด/คำค้น/ตัวกรองเดิม

## API อ่านใหม่

| Path ใต้ `/api/ipd/patients/:an` | ผลลัพธ์ |
|---|---|
| GET `/prescription-dates` | วันที่เริ่มรอบและจำนวนใบที่มีจริง |
| GET `/prescriptions?workdate=YYYY-MM-DD` | ใบสั่งยาของ AN/HN ในรอบที่เลือก |
| GET `/prescriptions/:prescriptionno?workdate=YYYY-MM-DD` | หัวใบและรายการยา; 404 ถ้าไม่ใช่ของ AN/HN/รอบนั้น |

ทุก endpoint ตรวจ JWT, AN และ active ward ปัจจุบันด้วย resolver เดิม ใช้ HN จาก backend ไม่รับ HN override ตรวจวันที่/array/รูปแบบเลขใบก่อนอ่าน ใช้ SQL parameters ทุก key และปิด mutation methods

Source เดิม `checkscreen` ส่ง prescriptionno ไปเทียบ `prescription.meditemindex` จึงไม่ใช้ผลนั้นมาอ้างว่า “จัดยาแล้ว” ใน viewer แสดงจำนวนแถวที่มีเวลาส่งต่อ/ตรวจจริง และ timestamp ในรายการยา โดยไม่ตีความว่าเป็นสถานะจ่ายยาครบถ้วน ตัวกรอง production-room ของ native ยังไม่อยู่ในขอบเขตห้อง IPD 001/010 รอบนี้

## ผลตรวจ

- `npm test` ผ่าน 31 กรณี เพิ่มการเปิดใบผิด AN/ผิดรอบ/วอร์ดผิด/ไม่ login/HN override/รูปแบบผิด/DB outage และป้องกัน POST/PUT/DELETE
- Frontend build และ ESLint ไฟล์ที่แก้ผ่าน ไม่มี dependency เพิ่ม
- ฐานข้อมูลจริง: ตัวอย่าง 1 ใบ 5 รายการ เทียบชุด prescriptionno กับ query native และชุด itemindex กับ detail เดิมตรงกันทุกตัว จำนวนวันตรงกับจำนวนใบ และทุกรายการตรงเลขใบที่เลือก เวลา list ประมาณ 246 ms และ detail พร้อมตรวจ parity ประมาณ 217 ms เป็นตัวอย่าง ไม่ใช่ SLA
- Browser กับผู้ป่วยจริง: เลือกวันย้อนหลัง เปิดยา เปลี่ยนวันแล้วล้าง detail, refresh คงวันที่/เลขใบ, สลับ Medication Profile แล้วกลับมาคงใบเดิม ไม่มี alert
- ข้อมูลสมมติทดสอบเปลี่ยนระหว่าง 2 ใบในวันเดียวกันและตรวจรูปแบบ ไม่มีข้อมูลผู้ป่วยจริงในภาพตัวอย่าง

การเทียบชุดตัวอย่างไม่ใช่การรับรอง parity ทุกกรณี/ทุกสถานะของ Windows และไม่มีการเขียนข้อมูลธุรกิจหรือเปลี่ยน schema/index
