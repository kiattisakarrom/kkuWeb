# ใบเบิกย้อนหลังหลายวัน/รายเดือน: timeout และผลตรวจ 23 ต.ค. 2026

## สาเหตุที่ยืนยันได้

- ตัวกรองไม่ได้จำกัดจำนวนวัน รับช่วงเดือนและหลายเดือนได้ ไม่มี TOP หรือการตัดแถว
- ใบเบิกทุกหน้าเคยใช้ pool MSSQL ของหน้าทั่วไปโดยไม่ตั้ง requestTimeout จึงใช้ค่าปริยาย **15,000 ms** ของ node-mssql 10/Tedious
- ทดสอบห้องยา IPD / ชั้น 4 วันที่ 1–30 ก.ย. 2026 เกิด ETIMEOUT หลัง 15,235 ms โดย error middleware เดิมตอบว่า “เชื่อมต่อข้อมูลไม่ได้” เหมือนกรณีฐานเข้าไม่ได้
- เมื่อตั้ง pool timeout 120 วินาที query เดิมทำสำเร็จใน **51,283 ms** ได้ 605 แถว ส่วน PDF 19 หน้าใช้ **734 ms** จึงติดการรวมข้อมูล SQL เป็นหลักในกรณีที่ตรวจ
- Frontend และ Nginx ทั้ง 2 ชั้นเดิมรอ 60 วินาที ต่อให้แก้ SQL timeout อย่างเดียวก็ยังติดขีดจำกัดชั้นถัดไปได้
- ordercreatedate เป็น datetime และมี index อยู่แล้ว ไม่พบว่ามี CAST ครอบคอลัมน์วันใน query ปัจจุบัน การกล่าวว่าไม่มี index หรือ CAST ทำให้ใช้ index ไม่ได้จึงยังไม่มีหลักฐาน

## สิ่งที่แก้

- `repositories/requisitionMssqlSource.js` ใช้ pool แยกเฉพาะใบเบิกแบบ lazy ตั้ง **requestTimeout=120,000 ms ที่ pool** ตาม API ของ node-mssql 10 (การตั้ง request.timeout ไม่มีผลในรุ่นนี้) จำกัด 3 connections/acquire 15 วินาที ไม่แก้ pool ของ login/ผู้ป่วย
- ครอบคลุมทั้ง IPD, D/C, ER, ER (OPD), อาคารเภสัชกรรม, Fixed Stock, อาคารรังสี
- SQL aggregate ทั้ง 6 ฝั่ง MSSQL เพิ่ม OPTION (RECOMPILE) เพื่อให้ optimizer พิจารณาช่วงวันที่/ประเภทของคำขอปัจจุบัน แทนใช้แผนเก่าร่วมระหว่างวันเดียวกับทั้งเดือน คง WHERE, JOIN, SUM, GROUP BY, ORDER BY, CInt และสูตรแพ็กเดิม ไม่มี NOLOCK/ตัดแถว/แบ่งวันแล้วปัดยอดซ้ำ
- OPD source ที่เตรียมไว้เพิ่ม query timeout จาก 10 เป็น 120 วินาที คง connectTimeout 8 วินาทีและเงื่อนไขเปิดแหล่งข้อมูลเดิม **ไม่เชื่อมตรวจ MySQL และไม่เปลี่ยน flags ที่ปิดไว้**
- Frontend รอรวมสูงสุด 300 วินาที เผื่อ ER อ่าน MSSQL แล้ว OPD ตามลำดับและสร้าง PDF ส่วน Nginx ทั้ง 2 ชั้นเพิ่มเป็น 300 วินาทีเฉพาะ `/api/reports/requisition-` เส้นทางอื่นยังใช้ 60 วินาทีเดิม
- ถ้า aggregate หมดเวลาตอบ 504 พร้อม “การรวมข้อมูลใบเบิกใช้เวลาเกินกำหนด กรุณาลองใหม่หรือลดช่วงวันที่” แยกจากเชื่อมต่อฐานไม่ได้ (503) และ frontend timeout แสดงข้อความเดียวกัน

ตัวเลข ER ในตารางเป็นข้อมูลดิบ MSSQL สำหรับวัด query ไม่ใช่ผลรายงาน ER รวม/แปลงรหัส และไม่ใช่ผล MySQL การจับเวลาทำตามลำดับเพื่อไม่ยิงงานหนักหลายชุดพร้อมกัน

- IPD ก่อน/หลัง hint ได้ SHA-256 ของทุก raw field ตรงกัน: `21139006cd4a0284378a43cd826a590d59397f6abc25b722e8b9357ae74a59ac` แถว 605 / PDF 19 หน้าเท่ากัน
- `tools/check-requisition-performance.cjs` รับ scope/from/to/timeout/mode (`baseline` ตัด hint, `current` ใช้ hint) อ่านอย่างเดียว พิมพ์เฉพาะจำนวน/เวลา/digest ไม่พิมพ์ข้อมูลยา/ผู้ป่วยหรือ credentials
- Backend regression 287/287 ผ่าน รวมทดสอบแยก pool/timeout ตามรุ่น driver, bindings, ช่วงเดือน/หลายเดือน, 504 ทั้ง 7 API, 503 กรณีเชื่อมต่อไม่ได้ และงบเวลาสอดคล้องกันทั้งเว็บ/2 proxies
- Frontend targeted ESLint และ production build ผ่าน
- ตรวจผ่าน browser หลัง restart backend: IPD วันที่ 1–30 ก.ย. แสดง PDF 19 หน้าได้จริง เปลี่ยนหน้าสุดท้าย/พอดีหน้าได้ ยอดรวม 605 รายการและช่องลงชื่อครบ บันทึกภาพ `requisition-month-loaded.png`

## ขอบเขตที่ยังต้องพิจารณา

การเพิ่มเวลารอช่วยให้ query ที่ต้องใช้มากกว่า 15 วินาทีทำจนจบ ไม่ได้ยืนยันว่าทุกช่วงวันที่จะเร็วหรือสำเร็จภายใน 120 วินาที หากข้อมูลมากกว่านี้หรือมี blocking ต้องตรวจ execution plan/IO/waits และพิจารณา covering index กับผู้ดูแลฐาน หรือทำงานสร้างรายงานเบื้องหลังต่อไป ยังไม่ได้เปลี่ยน index/schema หรือข้อมูลจริง

ตรวจ actual plan/ดัชนีต่อแล้ว ดู [ผลตรวจ SQL และดัชนี 23 ต.ค. 2026](REQUISITION-SQL-AUDIT-2026-10-23.md): พบ full scan/lookup/sort spill มีร่างดัชนี 2 ตัวที่ยังไม่สร้างจริง การทดลอง HASH GROUP แม้เดือน ก.ย. ผลตรง 24/24 แต่ย้อนหลัง 3 เดือนมีชื่อยา 6 แถวต่างตัวพิมพ์ใหญ่–เล็ก จึงยังไม่เปิดใช้ SQL ทางเลือกนี้ ผลเวลาเดิมด้านบนเป็นคนละรอบและมีผลของ cache ไม่ใช่ตัวเลขรับประกันความเร็ว

แก้และทดสอบใน local การใช้งานบนเครื่อง deploy ต้อง rebuild/restart backend/frontend และ reload Nginx ที่ใช้ config นี้ด้วย ไม่มีการ deploy จากงานนี้
