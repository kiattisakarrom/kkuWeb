# Screening — Stat รอจัด / Stat จัดแล้ว (ดูข้อมูล)

วันที่ตรวจ 18 ตุลาคม 2026 อ้างอิง `Screenning/ucScreenningMain.vb`, `Screenning/ucScreenning.vb` (`Showward`, `ShowPrescriptionHeader`, `ShowPrescriptiondetail`), `Screenning/cls/clsPrescription.vb`, `Screenning/cls/clspackagemaster.vb.vb` และ `Login/class/ClsUsers.vb:getRoom` ของ Windows รุ่นที่ผู้ใช้ให้

สถานะต่อยอดหลังเฟสนี้: เพิ่ม [Continue รอจัด](IPD-SCREENING-CONTINUE.md) แล้ว โดยใช้ห้องยา/รอบ/ตารางและการนำทางร่วมกัน รายงานผล Stat ด้านล่างเป็นหลักฐานของเฟส Stat

## การใช้งาน

เมนูเดิม ห้องยา IPD → Screening เปิด `/ipd/screening` เริ่ม Stat รอจัด เลือกปุ่ม Stat จัดแล้วเพื่ออ่านรายการอีกสถานะ ใช้กรอบเดิม: วอร์ดซ้าย → ใบสั่งยาบน → รายการยาล่าง พร้อมเมนูและแถบผู้ใช้เดิม

- ตัวเลือกห้องยาของ Screening อ่าน **ทุกห้องจาก `ms_room`** ตาม `getRoom` ของ Windows ไม่จำกัดเฉพาะห้องที่หน้า login อนุญาต เริ่มด้วยห้องจาก session แล้วเลือกห้องอื่นได้ทั้งสองโหมด ตัวเลือกนี้ใช้ร่วมกันใน Screen container สำหรับโหมดที่จะเพิ่มต่อไป ปุ่มโหมดที่ยังไม่ทำยังปิดไว้
- การเปลี่ยนห้องใน Screening ไม่เปลี่ยนห้องยา login หรือบริบทหลัก IPD และหน้า patient profile; backend ตรวจห้องที่เลือกกับ master ทุกคำขอ ไม่รับชื่อห้องหรือ SQL จาก browser
- เลือกวันที่ ค้น AN/HN/เลขใบแบบตรงกันจากทุกวอร์ดภายในห้อง/รอบที่เลือก แสดงเฉพาะวอร์ดที่มีรายการ นับ distinct ใบสั่งยา
- เลือกวอร์ดแล้วเลือกใบเพื่ออ่านยา จำนวน ขนาด หน่วย เวลา/วิธีใช้/ข้อความที่บันทึก ประเภท เส้นทางตามตั้งค่า และสถานะ Off/Hold/ส่งจัด/พิมพ์ที่บันทึก คงค่าศูนย์ต่างจากข้อมูลว่าง แถว Off เป็นแดงและ Hold เป็นเหลืองตามกรอบตารางเดิม
- เปลี่ยนห้อง/โหมด/วันที่/ค้นหาแล้วล้างใบและยาเดิม ยกเลิกคำขอเก่าและตรวจ request key ก่อนแสดง แยกกำลังโหลด/ไม่มีรายการ/ฐานข้อมูลผิดพลาด มีปุ่มลองใหม่
- ดับเบิลคลิกใบหรือกดดูรายละเอียดผู้ป่วย ใช้ AN ของใบนั้นและวอร์ดปัจจุบันที่ตรวจจาก admission/bedmove เมื่อกลับคงโหมด ห้องยา วันที่ รอบ คำค้น วอร์ดของใบ และเลขใบเดิม หากไม่มี admission ปัจจุบันที่เปิดได้ แสดงข้อความแทนการใช้วอร์ดเก่าของใบ
- ดูอย่างเดียว ปิดปุ่ม Screen/จัด/ส่งเครื่อง/พิมพ์/ยกเลิก และไม่มี mutation/hardware route ใน viewer

## เงื่อนไขจากต้นฉบับที่คงไว้

| ระดับ | Stat รอจัด | Stat จัดแล้ว |
| --- | --- | --- |
| วอร์ด | `genorderdatetime IS NULL`, ความถี่ S/E/STAT, `ordertype <> '1'` | `genorderdatetime IS NOT NULL`, ความถี่ S/E/STAT, `ordertype <> '1'` และ **`prioritycode NOT LIKE '%C%'`** |
| ใบ | gen ว่าง, S/E/STAT, non-home, active ward | gen ไม่ว่าง, S/E/STAT, non-home, active ward; **ไม่เพิ่ม priority exclusion ของยอดวอร์ด** |
| ยา | gen ว่าง, S/E/STAT ของใบที่เลือก | gen ไม่ว่าง, S/E/STAT ของใบที่เลือก |

กรองแหล่งส่งด้วย `fromlocationname = roomname+'['+roomcode+']'` จาก master จริง ใช้ SQL parameter ทั้งห้อง วัน คำค้น วอร์ด และเลขใบ ไม่กรอง void/Hold ทิ้ง เพราะ source เดิมคอมเมนต์เงื่อนไขเหล่านี้ไว้

รอบเริ่ม 08:00 ของวันที่เลือก เมื่อเวลาปัจจุบันกรุงเทพฯ ก่อน 08:00 ต้นฉบับถอยวันที่เลือกหนึ่งวัน **รวมการเลือกวันย้อนหลัง** ยอดวอร์ดสิ้นสุดวันถัดไป **07:59:00** แต่ใบและยาสิ้นสุด **07:59:59** คงความต่างนี้ไว้พร้อมข้อความที่หน้าจอ ส่ง `workdate` ที่ backend คำนวณแล้วให้ตารางลูกเพื่อไม่เปลี่ยนรอบระหว่างเลือกตอนข้าม 08:00 โหลดใหม่จะคำนวณรอบอีกครั้ง

`Screen แล้ว` หมายถึงมี `genorderdatetime` ตามต้นฉบับ ไม่ใช้ยืนยันว่าได้บริหารยาแก่ผู้ป่วยแล้ว แสดงวัน Screen ในหัวใบและเวลาจริงในรายการยา

รายละเอียดเพิ่มเงื่อนไขห้อง/วอร์ด/non-home/active ward และ HN/AN ที่อ่านจากหัวใบฝั่ง server เพื่อไม่ปนข้ามบริบท หากเลขใบชี้หลายตัวตนผู้ป่วยจะปฏิเสธ ไม่เปิดรายละเอียดโดยรับ HN จาก client

**ขอบเขตที่ยังต่างจากตาราง Windows:** แสดงแถว `prescription` ที่บันทึกจริง ไม่เรียก logic แตกซอง/คำนวณจำนวนต่อเวลาสำหรับเครื่อง JVM หรือสร้างรายการพิมพ์ จึงไม่อ้างว่าจำนวนแถว/จำนวนต่อซองเท่าตารางหลัง native แตกซอง แสดง QTY ที่บันทึก พร้อมเวลา/ข้อความดิบและเส้นทางตาม master; ไม่มีการคำนวณขนาดยาทดแทนหรือ side effect

## API และประสิทธิภาพ

GET ที่ต้องมี JWT:

- `/api/ipd/screening/options` → รายการห้องจริง
- `/api/ipd/screening/wards?roomCode=...&mode=stat-wait|stat-finished&orderdate=...&search=...`
- `/api/ipd/screening/prescriptions?...&wardCode=...&workdate=...`
- `/api/ipd/screening/prescriptions/:prescriptionno?...&wardCode=...&workdate=...`

ใช้ MSSQL pool ร่วมตลอด backend ไม่ connect/close global ต่อ request; options อ่านครั้งแรก รายการวอร์ด/ใบอ่านเมื่อบริบทเปลี่ยน รายละเอียดยาอ่านเมื่อเลือกใบ ใช้ EXISTS/OUTER APPLY สำหรับ master ไม่ขยายซ้ำจาก join และไม่มี HTTP/SQL lookup ต่อแถวยาจาก browser ใช้การแปลงวันแบบ `CONVERT` แทน `FORMAT` และเรียงรหัสวอร์ดตัวเลขด้วย CASE/CONVERT ที่เข้ากับ compatibility ของฐานจริง (ฐานนี้ไม่รองรับ `TRY_CONVERT`)

เส้นทาง Stat นี้ใช้ MSSQL ตาม Windows ไม่มี MySQL; ส่วน MySQL ในหน้าอื่นยังคงเตรียมไว้ตามข้อกำหนด [การเชื่อมต่อ](DATABASE-CONNECTIVITY.md)

## ผลตรวจ

- Backend tests **87/87 ผ่าน** ครอบคลุม auth, ห้องที่เลือกจริง/ห้อง login ไม่เปลี่ยน, mode ไม่ปนกัน, วันและรอบก่อน/หลัง 08:00, ปฏิเสธตัวกรองผิด/ข้ามใบ, error ต่างจาก empty, ปิด writes/hardware และ patient return context
- Frontend production build และ ESLint เฉพาะไฟล์ที่เปลี่ยนผ่าน
- ฐานจริง: อ่านตัวเลือกห้องได้ **19 ห้อง** เทียบ manual SQL ของ native กับ repository ในรอบที่มีข้อมูล: รอจัด **2 วอร์ด/2 แถวหัวใบ**, สุ่มรายละเอียด **4 แถวยา**; จัดแล้ว **27 วอร์ด/80 แถวหัวใบ**, สุ่มรายละเอียดหนึ่งใบต่อวอร์ดที่มีหัวใบรวม **43 แถวยา** ยอด distinct ใบรายวอร์ด, key/field หัวใบ และค่า itemindex/รหัสยา/ชื่อ/ขนาด/จำนวน/ความถี่/วัน Off/Hold/ส่งจัด ตรงกันในตัวอย่างที่ตรวจ ไม่บันทึกรหัสหรือข้อมูลผู้ป่วยลงเอกสาร/log
- หลัง restart backend ทดสอบ API จริงด้วยบัญชีที่ผู้ใช้ให้: options 200 (19 ห้อง), รอจัด 001/จัดแล้ว 001/จัดแล้ว 002 ตอบ 200; ตัวอย่างเวลา options **78 ms**, วอร์ด **332–467 ms**, หัวใบ **138 ms**, รายละเอียดยา **211 ms** เป็นการวัดเฉพาะรอบนี้ ไม่ใช่การรับรองเวลาโหลดทุกช่วงหรือทุกห้อง
- Browser ข้อมูลสมมติ: เมนูเข้า Screen, สลับรอจัด/จัดแล้ว, เลือก 001/002/010, เปลี่ยนวันแล้วกดค้นหาใช้รอบใหม่/ล้างรายการเดิม, ค้นใบเฉพาะวอร์ด/ไม่พบ, สลับใบไม่ค้างยาเดิม, Off และ 0, ฐานล้มเหลว/ลองใหม่/ผลว่าง และดับเบิลคลิกผู้ป่วยย้ายวอร์ดแล้วกลับโหมด/ห้อง/วัน/ใบเดิมผ่าน ภาพยืนยันใช้ข้อมูลสมมติทั้งหมด

ยังต้องตรวจรับข้อมูลจริงทุกห้อง/รูปแบบเวลาและตัวอย่าง master ซ้ำหรือหาย รวมถึงงานแตกแถวเวลาเพื่อการแสดงผลหากต้องการตารางระดับซองตาม native ส่วน Continue/All/Take-home/Robot/ภาพใบสั่งยาเป็นงานถัดไป ไม่ถือว่าโหมดเหล่านั้นเสร็จจากการใช้ container ร่วมกัน
